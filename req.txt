# Feature Implementation: AI-Generated Generic DQ Rule Descriptions During Template Upload

Act as a senior backend engineer and software architect. Analyze the existing DQHub codebase and implement the following feature end to end, adhering to the existing architecture, coding standards, database models, API conventions, and UI integration patterns.

## 1. Business Requirement

Enhance the existing template-upload workflow to support AI-generated generic Data Quality (DQ) rule descriptions.

When a user uploads a template through the UI, an AI-generated description should be created for each applicable DQ rule in real time, but **only when the AI-description feature flag is enabled on the UI**.

The generated descriptions must be shown to the user for review before they are persisted. The user must be able to choose between:

1. **Approve AI-generated description:** Accept the suggested description and save it to the database.
2. **Keep existing description:** Reject the AI-generated suggestion and retain the existing description.

The final, user-confirmed description must be stored in the existing Rule table. The Rule table must also contain a Boolean flag indicating whether the final description was generated by AI.

This must be integrated into the existing workflow rather than implemented as an isolated demonstration or a separate application.

## 2. Expected End-to-End Workflow

Implement the following flow:

1. The user enables the AI-generated description feature flag in the UI.
2. The user uploads a DQ template.
3. The existing template-upload API receives and processes the uploaded template using the current validation and parsing logic.
4. When the feature flag is enabled, identify the applicable DQ rules and generate generic descriptions using the project's existing AI/LLM integration, if available.
5. Return the generated descriptions to the UI in the upload response or through an appropriate existing asynchronous interaction, depending on the current architecture.
6. Display the AI-generated descriptions alongside their corresponding existing descriptions.
7. Allow the user to approve each AI-generated description or retain the existing description.
8. Submit the user's decisions and the final descriptions to the backend.
9. Validate the submitted decisions and persist the final descriptions in the existing Rule table.
10. Set the AI-generated-description flag according to the origin of the final saved description.

**Important:** Do not permanently overwrite existing descriptions or commit AI-generated descriptions as final before the user confirms the changes.

If the flag is disabled, preserve the existing template-upload behavior without invoking AI generation.

## 3. Database Changes

Inspect the existing Rule SQLAlchemy model, database schema, migrations, and description fields before implementing changes.

Add a Boolean column to the Rule table to indicate whether the saved description originated from AI.

Suggested column name:

`is_description_ai_generated`

Expected semantics:

* `true`: The final description was generated by AI and approved by the user.
* `false`: The final description was retained from the existing description or was otherwise not AI-generated.

Requirements:

* Choose a safe default consistent with existing records and business rules.
* Ensure existing rows remain valid.
* Create the appropriate database migration using the repository's existing migration framework.
* Update the SQLAlchemy model and any relevant schemas, serializers, and response models.
* Ensure the flag accurately reflects the origin of the final persisted description.
* Do not set the flag to `true` merely because an AI suggestion was generated or displayed.
* Do not add a duplicate Rule table or duplicate description field unless the existing schema makes this unavoidable.

If the existing architecture separates rule definitions, rule libraries, and their mappings, determine which entity owns the canonical description and persist the final result in the existing Rule table as required.

## 4. API Design and Integration

First, locate the existing template-upload endpoint and trace its complete execution flow.

Implement the necessary API changes using the existing framework, likely FastAPI, and follow the repository's established conventions.

Determine whether the feature should use:

* An enhanced template-upload endpoint that returns pending AI suggestions.
* A separate description-generation endpoint called during upload.
* A confirmation endpoint that persists user-approved decisions.

Use the smallest practical API change that fits the existing architecture. Do not create unnecessary endpoints.

### AI generation response

For each applicable rule, return sufficient information to associate the suggestion with the correct existing rule or pending template rule.

The response should include, where applicable:

* Stable rule identifier or temporary upload identifier.
* Rule name or rule type.
* Existing description.
* AI-generated description.
* Whether an AI suggestion was generated successfully.
* A status indicating whether user confirmation is pending.
* Relevant validation or generation errors.

Use the actual project's naming conventions and response schema rather than introducing arbitrary field names throughout the codebase.

### Confirmation request

When the user submits their decisions, the backend must:

* Identify each rule securely and unambiguously.
* Validate the user's decision.
* Validate that the submitted description corresponds to an allowed action.
* Save the approved AI description when the user approves it.
* Retain the existing description when the user rejects it.
* Update `is_description_ai_generated` accurately.
* Avoid persisting unconfirmed AI suggestions.
* Handle duplicate submissions and retries safely.
* Return a clear result for each processed rule.

If temporary rules are created during upload, ensure they can be associated with the confirmation request without prematurely publishing or permanently modifying them.

Do not trust a client-supplied rule ID, description, or approval status without validating it against the relevant persisted or pending upload state.

## 5. UI Integration

Inspect the existing UI implementation and its API integration points before changing anything.

When the feature flag is enabled:

* Show AI-generated descriptions during the template-upload workflow.
* Display the existing and suggested descriptions clearly.
* Provide an individual approval/rejection decision for each applicable rule.
* Allow the user to approve the AI description or continue with the existing description.
* Submit the final decisions to the backend.
* Display loading indicators during generation and saving.
* Display useful error messages and allow appropriate retries.
* Ensure the user can identify which descriptions are awaiting confirmation.

When the feature flag is disabled:

* Do not generate AI descriptions.
* Do not introduce additional confirmation steps.
* Preserve the existing user experience and API behavior.

Use the project's existing UI framework, component patterns, and feature-flag implementation. If the UI is in another repository, identify the precise API contract and provide the corresponding UI changes or clearly specify the integration points and required changes.

## 6. AI Generation Requirements

Inspect the existing LLM client, configuration, prompt templates, authentication, timeout handling, and error-handling mechanisms.

Reuse the existing AI integration if one is available. Do not introduce a new AI provider or hardcode API keys without explicit justification.

Generated descriptions must be:

* Generic and reusable across applicable datasets.
* Concise, clear, and business-readable.
* Consistent with the actual purpose of the DQ rule.
* Based on the rule's name, rule type, parameters, placeholders, and available metadata.
* Free from fabricated business meaning or unsupported assumptions.
* Independent of actual dataset values unless the existing business requirement explicitly requires those values.

For rules containing placeholders, generate descriptions that preserve the generic intent of the rule and do not accidentally expose or replace unresolved placeholders.

Do not send sensitive dataset contents or unnecessary connection information to the AI provider.

If generation fails for one rule, handle that failure gracefully and preserve the existing description. Do not silently save a failed or empty AI response as the final description.

## 7. Data Integrity and Security

Implement appropriate safeguards:

* Do not persist suggestions before confirmation.
* Do not overwrite existing descriptions when the feature flag is disabled.
* Validate all submitted descriptions and decisions server-side.
* Use database transactions where appropriate to maintain consistency.
* Prevent partial or inconsistent updates when saving multiple rules.
* Apply existing authentication and authorization rules.
* Prevent unauthorized modifications to rules outside the current upload or user's access scope.
* Avoid logging sensitive prompt content, credentials, or dataset values.
* Handle concurrent updates and repeated confirmation requests safely.
* Ensure failures during generation or confirmation do not corrupt existing rule data.

If the current upload flow creates or updates Rule records before confirmation, propose and implement the safest compatible approach to defer the relevant description updates until confirmation.

## 8. Performance and Reliability

* Do not block the existing upload flow with unnecessary AI calls when the feature flag is disabled.
* Avoid duplicate generation requests for the same rule during retries.
* Use appropriate request timeouts and bounded concurrency if multiple descriptions are generated.
* Follow existing synchronous or asynchronous patterns instead of introducing unnecessary infrastructure.
* Do not add Celery, RabbitMQ, schedulers, or new services unless the existing architecture genuinely requires them.
* Ensure the feature does not materially degrade the existing template-upload workflow.
* Preserve existing behavior for templates containing unsupported or invalid rules.

For a real-time user experience, prefer returning generated suggestions directly when practical. If generation duration or the current architecture makes that unsuitable, propose a compatible asynchronous alternative and explain the trade-offs.

## 9. Testing Requirements

Add or update unit tests and integration tests using the project's existing testing framework.

Cover at least the following scenarios:

1. Feature flag disabled: existing upload behavior remains unchanged.
2. Feature flag enabled: AI descriptions are generated for applicable rules.
3. AI suggestion is displayed but not yet confirmed: the existing persisted description remains unchanged.
4. User approves the AI description: the new description is persisted and the AI flag is `true`.
5. User rejects the AI suggestion: the existing description is retained and the AI flag is `false`.
6. AI generation fails: the existing description is preserved.
7. AI returns an empty or invalid description: no invalid description is saved.
8. Invalid or unauthorized rule identifiers are rejected.
9. Confirmation is submitted more than once: no unintended duplicate effects occur.
10. Database transaction fails: changes are handled consistently.
11. Existing Rule records without the new flag remain compatible.
12. Mixed decisions for multiple rules are processed correctly.
13. Concurrent changes to a rule do not silently overwrite newer data.
14. Existing template-upload tests continue to pass.

Mock the AI provider in unit tests. Do not make real AI calls during automated test execution.

## 12. Non-Negotiable Constraints

* Do not rewrite unrelated parts of DQHub.
* Do not invent repository files, endpoints, model attributes, or existing infrastructure.
* Do not assume the upload API creates permanent Rule records before inspecting the code.
* Do not persist AI-generated descriptions without explicit user confirmation.
* Do not lose the existing description when a user rejects an AI suggestion.
* Do not set the AI flag to `true` until an AI-generated description has been approved and successfully persisted.
* Do not call the AI provider when the feature flag is disabled.
* Do not introduce additional infrastructure without demonstrating why it is necessary.
* Do not provide pseudocode in place of implementation when the repository and tools permit actual code changes.
* Preserve backward compatibility with existing API consumers and database records.

**Start by inspecting the repository. Do not immediately generate code based on assumptions. Once the existing upload flow and Rule persistence logic are understood, implement the smallest complete, production-ready change that satisfies the requirements.**
